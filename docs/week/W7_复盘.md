### 2. 流式输出（W7D3）

**技术实现**：SSE + LLM `stream: True`

| 指标 | 非流式 | 流式 | 改善 |
|---|---|---|---|
| **首字延迟** | 6675ms | **1577ms** | **4.2×** |
| 来源展示 | 6675ms | **736ms** | **9.1×** |
| 完整答案 | 6675ms | 6982ms | 略慢 |

**事件设计**：
```
event: meta   → 来源 + 检索耗时（用户马上看到出处）
event: token  → 逐字
event: done   → 首字延迟 / 总耗时 / 字数 / 是否拒答
event: error  → 异常
```

## 四、关键认知

### 认知 1：真正的用户测试，会暴露你完全没想到的问题

**我以为**：API 返回了 `sources[]`，字段齐全，溯源已经做了。

**用户说**："不知道哪来的材料【1】"

**教训**：**数据完整 ≠ 用户理解**。给结构化数据不加编号对应，等于给了半套方案。

### 认知 2：延迟问题的根源是 LLM，不是检索

| 环节 | 耗时 | 占比 |
|---|---|---|
| 检索（含 embedding） | ~500ms | 7% |
| LLM 生成 | ~6000ms | **90%** |

**所以优化方向是流式输出，不是"优化检索"**——这点想错会浪费很多时间。

### 认知 3：能力边界要写在用户看得见的地方

T2 说："不知道能问什么""能用的地方不多"

**原因**：能力边界只写在 `KNOWN_ISSUES.md` 里，用户看不到。修复后才放进页面顶部。

**教训**：**工程文档是给团队的，产品说明是给用户的，两者都要有。**
