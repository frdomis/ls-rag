## 二、四个技术结论（都带归因）

### 1. 元数据过滤是最大功臣：+15.1pp

- 19/33 → 24/33（+15.1pp）
- **原因**：139 块语料中 125 块是院校章程，模板句（"录取分数线""录取规则"）在纯语义检索下挤占政策/分数线块
- **代价**：Q39（政策链接）因"政策"关键词误路由，过滤后反而未命中 → 靠空集兜底防漏召

### 2. rerank 有效但有天花板：+2 题

- 24/33 → 26/33（+6.1pp）
- **原因**：救回 2 道"排序失误"类题（答案在候选池但没进 top5）
- **天花板**：漏检 7 道中 4 道是"候选缺失"（Q15/Q17/Q18/Q33），**rerank 无能为力**
- **代价**：延迟 220ms → 1.2s（5.5 倍），千次 ¥0.5

### 3. query 改写无效，且与 rerank 重叠

- 24/33 → 25/33（+1 题，噪声范围）
- **改写 + rerank = 25/33 < 原始 + rerank = 26/33**（叠加反而 -1）
- **原因**：改写补了术语（"一辈子就一次"→"报考次数限制"），但语料用的是"报名次数"这类词，词面仍对不上；而 rerank 的语义匹配已经覆盖了口语理解
- **决策**：线上不启用改写

### 4. 多路 RRF 在小语料无增量

- 过滤 + 向量 = 24/33；过滤 + 多路 RRF = 24/33（+0）
- **原因**：过滤后候选池只剩 10-15 块，两路的 top5 高度重叠
- **但保留代码**：候选池 >20 时可能有效（charter 类 125 块）

## 三、方法学收获（面试主故事）

### 故事 1：三个 Qdrant 集合导致数字漂移

**现象**：W3 得出"混合检索没用"，W4 得出"混合检索有用 52.9% vs 47.1%"，数字前后矛盾。

**排查**：
```python
Invoke-RestMethod http://localhost:6333/collections
# → chunks(139) / ls_rag_docs_clean(2403) / ls_rag_docs_clean_200(200)
```
**三个集合同时存在，三个脚本各指一个。**

**修复**：统一到 `chunks`（139 点），point_id 用 `uuid5(NAMESPACE_URL, chunk_id)`，payload 存 chunk_id。

**结论**：**同源验证不做，所有对比实验都是假的。**

### 故事 2：id 空间不一致导致 RRF 空转

**现象**：混合检索"看起来在跑"，但效果一直等于单路。

**根因**：
```python
# 错误代码
chunks[idx].get("chunk_id", idx)   # 字段名是 id，不是 chunk_id
# → BM25 返回整数下标 (17, 16, 89...)，向量返回 hex (e7061bb895c2...)
# → RRF 在融合两个不相交的 id 集合
```

**修复**：强制 `cid_of()` 只认 `id/chunk_id/chunkId`，缺失就报错，不回落下标。

**结论**：**字段名兜底 = 静默错误，比崩溃更危险。**

### 故事 3：30.5% 的要点语料里根本没有

**现象**：要点覆盖率一直上不去（38.3%），归因全是 `miss_recall`。

**排查**：逐个要点去全语料搜索 4-gram → **118 个要点里 36 个（30.5%）语料根本没有**。

**修复**：分母从 128 改成 80（语料可支撑要点），4 道不可答题从分母排除。

**结论**：**"检索失败"和"知识库缺失"必须分开量化，否则会优化错方向。**
